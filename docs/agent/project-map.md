# Project Map — RevFactor Hub

RevFactor Hub is an internal operations hub for a short-term rental revenue management consultancy. Phase 1 is for 2-3 internal users and is not client-facing.

## Stack

- Frontend: Next.js 16 App Router, React 19, shadcn/ui, Tailwind CSS v4
- Backend: Supabase PostgreSQL, Auth, Storage, Edge Functions
- Deployment: Vercel
- Package manager: pnpm

## App Structure

- `app/layout.tsx` — root layout with Sonner toaster and theme provider.
- `app/login/page.tsx` — password and magic-link login.
- `app/auth/callback/route.ts` — magic-link callback handler.
- `proxy.ts` — Next.js 16 middleware replacement for session refresh and auth redirects.
- `app/(authenticated)/layout.tsx` — authenticated shell with sidebar and top bar.
- `app/(authenticated)/page.tsx` and `dashboard-view.tsx` — dashboard home.
- `app/(authenticated)/agent-studio/` — governed internal AI sandbox. Playground runs persist conversations, sanitized source snapshots, tool traces, generation and retrieval token/cost/latency, ratings, and audit events. Knowledge retrieval is selectable per run (`keyword`, `hybrid`, or diagnostic `compare`); the Inspector exposes the exact supplied passages, keyword/semantic/hybrid ranks, embedding model, fallback reason, and retrieval cost. The optional **Pricing & Performance flow pilot** executes an internal LangGraph TypeScript graph (`classify → evidence check → draft → client-ready check`) and writes each observable node to the existing Trace inspector; it never sends or mutates external data and is not attached to production behavior. DeepSeek V4 Flash 0731 is an evaluation candidate with a server-enforced synthetic-only boundary: the UI disables it for real clients, the action rejects bypasses before loading context, and only synthetic evaluations include it. Saved runs can be reopened in the Playground with their client, model, playbook, message history, sources, traces, and inspector state restored; the original run remains immutable and continuing creates a new ledger entry (a teammate's run opens as a conversation copy). The right-side Studio Coach reviews a completed run plus up to four comparable runs, teaches from their evidence/feedback, proposes an instruction patch, and produces editable answer/negative-performance/clarify/escalate workflow scenarios. The negative-performance scenario verifies the benchmark, separates facts from possible causes, and routes to a client-ready answer, internal brainstorm, or human escalation. Coach changes can be applied to the browser session or saved only as a new draft playbook version. It also manages immutable playbook versions (`draft → testing → approved → production`), regression/prompt-injection evaluations, Assembly shadow captures, integration health, budgets, retention, and two-person production approvals. It remains read-only toward Assembly and PriceLabs.
- `app/(authenticated)/knowledge/` — internal Knowledge base plus agent-answer governance and visual Agent Flows. Articles can be FAQs, policies, SOPs, guides, or templates. Internal publication is separate from client-safe approval; only published, client-safe, approved, `agent_enabled`, currently indexed articles enter hybrid retrieval; exact keyword fallback preserves availability while indexing is unavailable. The editor stores a canonical question, approved short answer, escalation guidance, verification source, and review date. Approval automatically attempts indexing, and the article/detail and Insights UIs expose index status, passage previews, token/cost metadata, failures, and manual re-indexing. The Agent Flows tab lists governed n8n-style workflow maps; `/knowledge/flows/[id]` provides a React Flow palette/canvas/inspector editor, graph validation, explicit draft saves, immutable lifecycle versions, and audit history. A production flow is eligible for an explicit future playbook/agent attachment; promotion alone does not change runtime behavior.
- `app/(authenticated)/clients/` — client list, detail pages, credentials server actions.
- `app/(authenticated)/listings/` — listings table and listing detail dashboard.
- `app/(authenticated)/reservations/` — PriceLabs reservations browser (added 2026-07-31): server-side filtered/paginated table (50/page) driven entirely by URL searchParams (`client`, `listing`, `from`/`to` on check-in, `q`, `sort`, `dir`, `page`), gated on `reservations:view`. Data layer `lib/reservations.ts` reads the `pricelabs_reservations_cache` matview and hardcodes `booking_status = 'booked'` (cancelled excluded everywhere by product decision). `components/reservations/recent-reservations-card.tsx` is the shared "Recent Reservations" card on client detail (after Adjustments) and listing detail (between KPI cards and tabs, passed as a server-rendered `reservationsCard` slot prop into the client `ListingDetail`). Per-client Grant-style report export (added 2026-07-31): `GET /clients/[id]/export?from&to&asOf&dateField` (session-authenticated route handler, `reservations:view` checked inside — the matview has no RLS) builds a styled multi-sheet ExcelJS workbook: Summary dashboard (KPIs, listing/channel breakdowns with booking-window segments, embedded PNG charts, monthly pickup, occupancy, current-vs-previous listing tables), Reservations/Previous Period/Last Year detail tables (Excel tables with autofilter; Last Year hidden), Comparison, hidden Occupancy and \_ChartData. Module split: pure period/aggregation helpers `lib/reservations-export.ts` → model `lib/reservations-report-model.ts` → service (fetch+model+workbook, 50k cap) `lib/reservations-report.service.ts` → ExcelJS layout `lib/reservations-workbook.server.ts` + SVG→PNG charts via sharp `lib/reservations-chart.server.ts`. Occupancy source: `report_metrics` (latest completed report run, monthly). Dialog trigger `components/clients/export-reservations-dialog.tsx` in the client-detail action row. Unit tests in `lib/__tests__/` (vitest, `pnpm test`).
- `app/(authenticated)/tasks/` — task board, task dialog, task server actions.
- `app/(authenticated)/roadmap/` — ideas, roadmap kanban, votes, comments, post dialogs.
- `app/(authenticated)/pipeline/` — sales pipeline board/table/completed views, lead detail, import/export, Assembly contract actions. Lead detail is served two ways from one server component (`pipeline/[id]/lead-detail-content.tsx`): the full page at `pipeline/[id]/page.tsx` (hard loads: paste/refresh/share) and a modal via the intercepting route `@modal/(.)pipeline/[id]` (client-side clicks from board/table/completed). `lead-detail.tsx` takes `variant: "page" | "modal"`; the Dialog shell is `lead-detail-modal.tsx`, skeleton shared with `loading.tsx` via `lead-detail-skeleton.tsx`.
- `app/(authenticated)/@modal/` — parallel-route slot rendered by the authenticated layout (the app's only intercepting/parallel routes, added 2026-07-13). Contains `default.tsx` (null), a required catch-all `[...catchAll]/page.tsx` (null — clears the modal on soft navigations away), and `(.)pipeline/[id]/page.tsx` (the lead modal). See `decisions.md` 2026-07-13 before adding more intercepted routes.

(The Recurring-expenses tab was removed; costs are managed only through expenses.)
- `app/(authenticated)/settings/` — account, clients, listings, users, roles, boards/tags, onboarding settings.
- `app/(authenticated)/calendar/page.tsx` and `notes/page.tsx` — calendar and notes views.
- `app/(authenticated)/adjustments/` — Adjustments queues: "Waiting on us" first (status `needs_info` ∪ non-closed rows whose last comment is external — the internal bottleneck, hidden when empty), then triage (open by urgency+age with stale flags and a "client escalation" flag; excludes `needs_info`), "awaiting control" mini-queue (inline PriceLabs link + one-click Confirm control + setup verify hint), recently closed collapsed to 3. Rows show a comment count (amber "needs reply" when last comment is external) and click through to the internal detail modal. Client filter, create/edit dialog (Type + Origin selects with per-type conditional fields from `ADJUSTMENT_TYPE_CONFIG`; `setup` forces single-listing and hides target/dates/booking window; hostpricing-role users get the origin locked to HostPricing — also forced server-side in `createAdjustment`; create copies share link + opens the WhatsApp group; edit only while status is in `OPEN_STATUSES`, enforced in `updateAdjustment`), server actions. HostPricing-origin tickets in `open` read "Pending approval" with Approve/Deny labels (same statuses underneath).
- `app/(authenticated)/adjustments/[id]/` — internal adjustment detail ("authed core", richer than the public card; never merged with it): all fields incl. `origin_message`/requester/creator, origin-styled comments (violet hostpricing / amber client left accents), append-only status-history timeline, transition buttons incl. "Needs info" (note required; internal comment auto-reopens). Opens as a Dialog via the intercepting route `@modal/(.)adjustments/[id]` (pipeline pattern: shared `adjustment-detail-content.tsx` server component, `variant` "page"|"modal"); direct URL/refresh renders the full page. Notes support the comment hover bar (see below), internal thread replies (control-gated), and create-task links.
- `components/comments/` — shared comment hover action bar (`comment-action-bar.tsx`: 5 quick reactions 👍😀❤️😮🎉, curated emoji picker popover from `emoji.ts`, reply / create-task / copy) and `reaction-chips.tsx` (aggregated emoji chips, click to toggle). Used by the adjustment detail Notes and `tasks/task-comments.tsx`; the parent row must be `relative group/comment`.
- `app/api/v1/leads/route.ts` — outbound Leads Read API (GET) for marketing's tracking stack: API-key auth (`Authorization: Bearer rvf_live_…`, scope `leads:read`), keyset pagination via `updated_since` + `cursor`, per-lead attribution and funnel timeline. Reads through the admin client, so its column projection is the security boundary. See `integrations.md` and `docs/webhook-pipeline-integration.md`.
- `app/api/webhooks/new-lead/route.ts` — inbound lead ingest from the landing page (`x-webhook-secret`); accepts an optional `attribution` object parsed by `lib/lead-attribution.ts`.
- `app/a/[token]/page.tsx` — public adjustment card ("public shell + authed core" on the same URL): serves Open Graph meta and a read-only non-sensitive shell without a session (fetched via admin client by `public_token`; `proxy.ts` exempts `/a/` and `/api/` from the login redirect), and the full interactive card (notes, status transitions, resolver/control trail) when logged in.

- SEO metrics (created directly in Supabase, no migration): base table `seo_metrics_raw` is a near 1:1 dump of the Rankbreeze `listing-metrics` CSV (only Tags dropped) — cols `id` (PK), `download_date`, `airbnb_id`, `rankbreeze_id`, `listing_name`, `city`, `state`, `country`, `metric` (raw label), `guest_count`, `side` (`my listing`/`similar listing`), `period`, `value`. The read-side **VIEW** `seo_metrics` derives `metric_key` slugs (`city_rank`, `first_page_impressions`, `ctr`, `views`, `wishlists`, `booking_rate`, `overall_conversion`, `occupancy`, `adr`), normalizes `side` → `my`/`similar`, `NULLIF`s empty `period`, and LEFT JOINs `listings` on `airbnb_id` for `hub_listing_id`/`hub_client_id`+`listing_name`. **Write to `seo_metrics_raw`, never the view.** Loaded via Settings → Listings **SEO Metrics Upload** card (`seo-metrics-upload.tsx`): client parses with `lib/seo-metrics.ts` (`parseSeoMetricsCsv` → raw rows) then streams 2000-row chunks through `insertSeoMetricsChunkAction`; `clearSeoMetricsForUploadAction` first deletes rows scoped to the file's download date(s) **and** its Airbnb IDs (plus null-ID rows when the file has them), so re-uploading replaces rather than duplicates and partial/single-listing Rankbreeze exports refresh only their own listings without wiping the rest of that date's snapshot. Migration `040_seo_metrics_read_policy.sql` added a SELECT policy (`has_permission('listings','view')`); writes stay admin-client only. The listing detail page uses it to build the **Rankbreeze link** (`https://app.rankbreeze.com/rankings/<rankbreeze_id>`) by matching `airbnb_id` against both `listings.listing_id` and the numeric ID inside `airbnb_link` — beware: many `listings.listing_id` values are PriceLabs IDs or UUIDs, not Airbnb IDs, so `airbnb_link` is the more reliable join key (19 vs 210 of 251 listings matched, 2026-07-08).
- Report Builder (migration `035_report_builder.sql`): `report_runs` (ingestion state machine + observability + pruned `raw_envelope`), `report_listings` (listing attrs, `listing_id` text PK), `report_metrics` (monthly metrics, grain listing × month × run), `report_group_overrides` (Group Name → client fallback). Adds `idx_listings_listing_id`.
- RLS hardening (migration `038_rls_hardening.sql`, 2026-07-03): all SELECT/write policies are permission-based via `has_permission` (see `conventions.md` and `decisions.md`); adds the `clients_basic` view and the `profiles_role_guard` trigger.

## Domain Terms

- ADR: Average Daily Rate, revenue divided by nights sold.
- RevPAR: Revenue Per Available Room, revenue divided by total available nights.
- Occupancy: percent of available nights booked.
- Pacing: how bookings track versus a comparison period or booking window.
- PMS: property management system, such as Hostaway or Hospitable.
- PriceLabs: dynamic pricing tool; listings have unique PriceLabs IDs.
- MPI: Market Performance Index, listing occupancy divided by market occupancy.
