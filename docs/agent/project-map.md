# Project Map — RevFactor Hub

RevFactor Hub is an internal operations hub for a short-term rental revenue management consultancy. Phase 1 is for 2-3 internal users and is not client-facing.

## Stack

- Frontend: Next.js 16 App Router, React 19, shadcn/ui, Tailwind CSS v4
- Backend: Supabase PostgreSQL, Auth, Storage, Edge Functions
- Deployment: Vercel
- Package manager: pnpm

## App Structure

- `app/layout.tsx` — root layout with Sonner toaster and theme provider.
- `app/login/page.tsx` — password and magic-link login.
- `app/auth/callback/route.ts` — magic-link callback handler.
- `proxy.ts` — Next.js 16 middleware replacement for session refresh and auth redirects.
- `app/(authenticated)/layout.tsx` — authenticated shell with sidebar and top bar.
- `app/(authenticated)/page.tsx` and `dashboard-view.tsx` — dashboard home.
- `app/(authenticated)/agent-studio/` — governed internal AI sandbox. Playground runs persist conversations, sanitized source snapshots, tool traces, generation and retrieval token/cost/latency, ratings, and audit events. Knowledge retrieval is selectable per run (`keyword`, `hybrid`, or diagnostic `compare`); the Inspector exposes the exact supplied passages, keyword/semantic/hybrid ranks, embedding model, fallback reason, and retrieval cost. Saved runs can be reopened in the Playground with their client, model, playbook, message history, sources, traces, and inspector state restored; the original run remains immutable and continuing creates a new ledger entry (a teammate's run opens as a conversation copy). The right-side Studio Coach reviews a completed run plus up to four comparable runs, teaches from their evidence/feedback, proposes an instruction patch, and produces editable answer/negative-performance/clarify/escalate workflow scenarios. The negative-performance scenario verifies the benchmark, separates facts from possible causes, and routes to a client-ready answer, internal brainstorm, or human escalation. Coach changes can be applied to the browser session or saved only as a new draft playbook version. It also manages immutable playbook versions (`draft → testing → approved → production`), regression/prompt-injection evaluations, Assembly shadow captures, integration health, budgets, retention, and two-person production approvals. It remains read-only toward Assembly and PriceLabs.
- `app/(authenticated)/agent-studio/onboarding-study/` — authenticated, `agent_studio:view`-gated local prototype comparing the unchanged Assembly form path with a deterministic guided-chat path. The chat uses browser-session state only, maps answers to the exact migration-042 payload families, asks year before month for dated launch/event branches, lets clients edit any prior response, confirms likely property-name or known-PMS spelling corrections, and converts recognized Airbnb hosting/editor links into canonical public `/rooms/<id>` links only after explicit confirmation. It blocks credential-shaped input, exports JSON plus a text transcript, and exposes only simulated submission; it has no Server Action or external integration call. The repository has the persistence contract but not the separate custom app's current question copy, so wording requires a side-by-side Assembly review before a client study.
- `app/(authenticated)/knowledge/` — internal Knowledge base plus agent-answer governance and visual Agent Flows. Articles can be FAQs, policies, SOPs, guides, or templates. Internal publication is separate from client-safe approval; only published, client-safe, approved, `agent_enabled`, currently indexed articles enter hybrid retrieval; exact keyword fallback preserves availability while indexing is unavailable. The editor stores a canonical question, approved short answer, escalation guidance, verification source, and review date. Approval automatically attempts indexing, and the article/detail and Insights UIs expose index status, passage previews, token/cost metadata, failures, and manual re-indexing. The root page has five URL-synced tabs (`?tab=`, legacy `published|drafts` map to Team): **Team** (all articles with All/Published/Drafts status pills, categories grid, search, tag filter), **Agent** (view switcher: "Pipeline" groups client-safe/agent-enabled articles by stage in `_components/agent-pipeline-panel.tsx` — indexing failed → live → enabled-indexing → needs review → approved-not-enabled → drafting; "Gates table" in `_components/agent-gates-table.tsx` lists every article with its four gates and inline governance switches — Published via publish/unpublish, Client-safe via `setArticleAudience` which resets governance, Agent enabled via approve/disable — plus review/index badges, a re-index button, and titles linking to the article), **Credentials** (shared team app logins from `team_credentials`, rendered by `_components/team-credentials.tsx` with mutations in `credentials-actions.ts`; the tab only renders with `team_credentials:view`), **Insights**, and **Agent Flows**. The Agent Flows tab lists governed n8n-style workflow maps; `/knowledge/flows/[id]` provides a React Flow palette/canvas/inspector editor, graph validation, explicit draft saves, immutable lifecycle versions, and audit history. A production flow is eligible for an explicit future playbook/agent attachment; promotion alone does not change runtime behavior.
- `app/(authenticated)/clients/` — client list, detail pages, credentials server actions.
- `app/(authenticated)/listings/` — listings table and listing detail dashboard.
- `app/(authenticated)/reservations/` — PriceLabs reservations browser (added 2026-07-31): server-side filtered/paginated table (50/page) driven entirely by URL searchParams (`client`, `listing`, `from`/`to` on check-in, `q`, `sort`, `dir`, `page`), gated on `reservations:view`. Data layer `lib/reservations.ts` reads the `pricelabs_reservations_cache` matview and hardcodes `booking_status = 'booked'` (cancelled excluded everywhere by product decision). `components/reservations/recent-reservations-card.tsx` is the shared "Recent Reservations" card on client detail (after Adjustments) and listing detail (between KPI cards and tabs, passed as a server-rendered `reservationsCard` slot prop into the client `ListingDetail`). Per-client Grant-style report export (added 2026-07-31): `GET /clients/[id]/export?from&to&asOf&dateField` (session-authenticated route handler, `reservations:view` checked inside — the matview has no RLS) builds a styled multi-sheet ExcelJS workbook: Summary dashboard (KPIs, listing/channel breakdowns with booking-window segments, embedded PNG charts, monthly pickup, occupancy, current-vs-previous listing tables), Reservations/Previous Period/Last Year detail tables (Excel tables with autofilter; Last Year hidden), Comparison, hidden Occupancy and \_ChartData. Module split: pure period/aggregation helpers `lib/reservations-export.ts` → model `lib/reservations-report-model.ts` → service (fetch+model+workbook, 50k cap) `lib/reservations-report.service.ts` → ExcelJS layout `lib/reservations-workbook.server.ts` + SVG→PNG charts via sharp `lib/reservations-chart.server.ts`. Occupancy source: `report_metrics` (latest completed run, monthly). Dialog trigger `components/clients/export-reservations-dialog.tsx` in the client-detail action row. Unit tests in `lib/__tests__/` (vitest, `pnpm test`).
- `app/(authenticated)/revenue-manager/` — internal, `revenue:view`-gated Revenue Manager preview. The current slice is a clearly labeled, read-only Ashwood fixture workspace with Today (one verdict/attention item), Profile, Decisions, and Evidence tabs. It runs deterministic local evidence gates, creates no database rows, exposes no Server Action, and has no PriceLabs/PMS/OTA write path. Migration 075 remains unapplied; future persisted listing mode should load through `lib/revenue-manager/repository.server.ts`.
- `app/(authenticated)/market-signals/` — internal, `market_signals:view`-gated Market Signals queue. It reads the applied migration-076 foundation through `lib/market-signals/repository.server.ts`, shows Needs Review/New Announcements/Changed/Watchlist/Reviewed/Markets, and exposes source and worker health. Migration 078 makes coordinate-matched market membership and monitoring readiness agent-managed. `lib/market-signals/predicthq.ts` owns the first replaceable provider adapter; `ingest.server.ts` owns one-market idempotent persistence; `jobs.server.ts` owns durable enqueue/lease/retry orchestration; and `vulnerability.server.ts` joins the complete approved cohort to current PriceLabs evidence while persisting only the top 25 exposures for each selected signal through an atomic RPC. Migration 082 adds cached/audited Signal Briefs and brief-bound append-only decisions plus transactional create/link Adjustment RPCs. Queue cards default to decision KPIs and one recommendation headline; the full governed brief expands on demand. Refresh actions enqueue work, and Market cards show latest job state, attempts, duration, and terminal error. The `CRON_SECRET`-protected worker is scheduled every minute in `vercel.json`, while source rows keep their own cadence. There is no notification or external pricing/stay-rule write path.
- `app/(authenticated)/tasks/` — task board, task dialog, task server actions.
- `app/(authenticated)/roadmap/` — project cards/detail, project-filtered or all-task roadmap kanban, task deadlines, votes, comments, and task dialogs.
- `app/(authenticated)/pipeline/` — sales pipeline board/table/completed views, lead detail, import/export, Assembly contract actions. Lead detail is served two ways from one server component (`pipeline/[id]/lead-detail-content.tsx`): the full page at `pipeline/[id]/page.tsx` (hard loads: paste/refresh/share) and a modal via the intercepting route `@modal/(.)pipeline/[id]` (client-side clicks from board/table/completed). `lead-detail.tsx` takes `variant: "page" | "modal"`; the Dialog shell is `lead-detail-modal.tsx`, skeleton shared with `loading.tsx` via `lead-detail-skeleton.tsx`.
- `app/(authenticated)/@modal/` — parallel-route slot rendered by the authenticated layout (the app's only intercepting/parallel routes, added 2026-07-13). Contains `default.tsx` (null), a required catch-all `[...catchAll]/page.tsx` (null — clears the modal on soft navigations away), and `(.)pipeline/[id]/page.tsx` (the lead modal). See `decisions.md` 2026-07-13 before adding more intercepted routes.
- `app/(authenticated)/onboarding/` — legacy client-level onboarding cards, resources, step actions, and comments. Migration `042_client_onboarding_runs.sql` adds the run-based data contract consumed by the separate Assembly onboarding app; the Hub UI has not switched to it yet.
- `app/(authenticated)/financials/` — super_admin-only payout cash dashboard, Profit First allocations, expenses, subscriptions, saved 12-month planning scenarios, and Relay bank statement import/reconciliation (Bank tab). (The Recurring-expenses tab was removed; costs are managed only through expenses.)
- `app/(authenticated)/settings/` — account, clients, listings, users, roles, boards/tags, onboarding settings.
- `app/(authenticated)/adjustments/` — Adjustments queues: "Waiting on us" first (status `needs_info` ∪ non-closed rows whose last comment is external — the internal bottleneck, hidden when empty), then triage (open by urgency+age with stale flags and a "client escalation" flag; excludes `needs_info`), "awaiting control" mini-queue (inline PriceLabs link + one-click Confirm control + setup verify hint), recently closed collapsed to 3. Rows show a comment count (amber "needs reply" when last comment is external) and click through to the internal detail modal. Client filter, create/edit dialog (Type + Origin selects with per-type conditional fields from `ADJUSTMENT_TYPE_CONFIG`; `setup` forces single-listing and hides target/dates/booking window; hostpricing-role users get the origin locked to HostPricing — also forced server-side in `createAdjustment`; create copies share link + opens the WhatsApp group; edit only while status is in `OPEN_STATUSES`, enforced in `updateAdjustment`), server actions. HostPricing-origin tickets in `open` read "Pending approval" with Approve/Deny labels (same statuses underneath).
- `app/(authenticated)/adjustments/[id]/` — internal adjustment detail ("authed core", richer than the public card; never merged with it): all fields incl. `origin_message`/requester/creator, origin-styled comments (violet hostpricing / amber client left accents), append-only status-history timeline, transition buttons incl. "Needs info" (note required; internal comment auto-reopens). Opens as a Dialog via the intercepting route `@modal/(.)adjustments/[id]` (pipeline pattern: shared `adjustment-detail-content.tsx` server component, `variant` "page"|"modal"); direct URL/refresh renders the full page. Notes support the comment hover bar (see below), internal thread replies (control-gated), and create-task links.
- `components/comments/` — shared comment hover action bar (`comment-action-bar.tsx`: 5 quick reactions 👍😀❤️😮🎉, curated emoji picker popover from `emoji.ts`, reply / create-task / copy) and `reaction-chips.tsx` (aggregated emoji chips, click to toggle). Used by the adjustment detail Notes and `tasks/task-comments.tsx`; the parent row must be `relative group/comment`.
- `app/api/v1/leads/route.ts` — outbound Leads Read API (GET) for marketing's tracking stack: API-key auth (`Authorization: Bearer rvf_live_…`, scope `leads:read`), keyset pagination via `updated_since` + `cursor`, per-lead attribution and funnel timeline. Reads through the admin client, so its column projection is the security boundary. See `integrations.md` and `docs/webhook-pipeline-integration.md`.
- `app/api/webhooks/new-lead/route.ts` — inbound lead ingest from the landing page (`x-webhook-secret`); accepts an optional `attribution` object parsed by `lib/lead-attribution.ts`.
- `app/a/[token]/page.tsx` — public adjustment card ("public shell + authed core" on the same URL): serves Open Graph meta and a read-only non-sensitive shell without a session (fetched via admin client by `public_token`; `proxy.ts` exempts `/a/` and `/api/` from the login redirect), and the full interactive card (notes, status transitions, resolver/control trail) when logged in.

## Domain Terms

- ADR: Average Daily Rate, revenue divided by nights sold.
- RevPAR: Revenue Per Available Room, revenue divided by total available nights.
- Occupancy: percent of available nights booked.
- Pacing: how bookings track versus a comparison period or booking window.
- PMS: property management system, such as Hostaway or Hospitable.
- PriceLabs: dynamic pricing tool; listings have unique PriceLabs IDs.
- MPI: Market Performance Index, listing occupancy divided by market occupancy.
